Inputs

.input styles a text box, a select and a textarea alike. .input.mono is for addresses and ids; .input.sm and .input.lg change its size. textarea.input.autosize grows as it's typed into, up to --max-h (320 px), where the browser supports field-sizing (elsewhere it keeps its size).

Fields

.field stacks a label, the input, then a .hint or an .err. .field.invalid turns it red; set aria-invalid="true" on the input as well, and point aria-describedby at the message. Dash.form does all of that for you. label.req adds a star, for a field that must be filled in. .field-label is the same label for a group that isn't one input (a row of choices).

Search boxes

.search wraps an input with an icon and an optional .count. Dash.search(input, { onChange, debounce, key, store }) calls onChange(query) once typing pauses; Escape clears it, / jumps to it, and .count(shown, total) fills the count. With store the last query comes back on the next visit.

    Selects

    Wrap a <select class="input"> in .select to give it the kit's arrow in place of the browser's. Inside a .field it is full width.

    Input groups

    .input-group joins an input to text and buttons around it: .affix for a unit or a prefix, .btn for an action, and a .select too.

    Checkboxes and radios

    .checkline is a checkbox or radio with its label. .checks stacks a few, and .checks.across puts them on one line. Give the group a name: role="group" (or radiogroup) and an aria-label, or a fieldset with a legend.

    Choices as cards

    .choices makes radios (or checkboxes) into cards: each a label.choice holding the input, then a .choice-body with a b and a .hint. The checked one is outlined in its tone (blue by default). --choice-min (200 px) is how narrow a card gets before they stack.

    Switches

    .switch is a checkbox drawn as a switch, for a setting that applies at once: <label class="switch"><input type="checkbox"><span class="track"></span> Label</label>. A tone colours it on.

    Sliders

    Dash.slider({ label, name, min, max, step, value, unit, tone, disabled }) writes a range input with its value beside it, and dash.js keeps the value current as it moves. By hand: <label class="slider"><span>Volume</span><input type="range" data-unit="%"><output>50%</output></label>. Inside a .field its name reads as the field's label.

    Dropping files

    .dropzone is a <label> around an input type="file", so a click chooses files, and files dropped on it go into the input (only the kinds its accept allows), with input and change events as if they had been chosen. The chosen names show in its .files; .over marks it while files are dragged over.

    Checking a form

    Dash.form(form, { rules, onSubmit }) says what is wrong under each field, instead of the browser’s bubbles. A field is checked once the reader leaves it changed, and what it says goes as soon as it is put right. Submitting checks all of them and goes to the first problem: in a closed part or another tab too.

    The fields’ own checks count first: required (spaces alone are no answer), type, minlength, pattern (its title is what it says), min, max, step, and setCustomValidity. Dash.datepicker and a strict Dash.combobox say what is wrong with their box. Then come your rules.

    • Rules: a function (value, values, input) per name, or a list of them. A text is the problem; anything else is fine. They run on empty fields too. A rule about another field ((v, all) => v !== all.password && …) runs again when that one changes. '' is the form as a whole.
    • Asking the server: an async rule is asked once the field is left, with “Checking…” meanwhile; once per text, and late answers are dropped. One that can’t answer says nothing, until the form is sent: then it stops it, and says why.
    • onSubmit(values, form, button) runs once all is fine, with the button busy; a second submit does nothing. What it throws shows above the buttons; with errors: { name: 'text' } on it, or in the answer’s body (as Dash.api’s errors carry), on those fields, until they are changed. Without onSubmit the form goes on as it would, and your own submit listener hears only of a right one.
    • Values: text as typed, a number box as a number (null when empty), one checkbox as true or false, several of a name as a list, a file as a File. Disabled fields are left out, and not checked.
    • Where it shows: in the field’s .err (made when there is none), as a .field-err under a box that is in no .field, or in an element with data-error-for="name"; a .form-error line is above the buttons. The boxes get aria-invalid, and aria-describedby with the hint kept. A field the server sent as .field.invalid keeps its words until it is changed.
    • Words: data-problem="Give the site’s address." on a field, or Dash.form.text for all (to translate them). None of the kit’s hold what was typed. label.req adds the star.
    • A button with formnovalidate skips the checks. Fields that are drawn again keep their marks; a whole form drawn again is followed by its id.

    It returns { el, values(), errors, check(which), error(name, text), fail(err), clear(), destroy() }. check() checks all, or a name, a list of names, or the fields in an element (a step of several), goes to the first problem and resolves to true or false. error(name, text) puts a text on a field until it is changed ('': the line). The same form made again has the new rules.

    Without code, and in a dialog

    <form data-validate> does the fields’ own checks, with no code. Dash.modal and Dash.dialog take rules ({}: just the fields’ own checks) and Dash.ask a check; they stay open until it is right. In a modal m.form is the handle, and an error from onAction with errors lands on the fields.

    Unsaved changes

    Dash.unsaved(form) watches a form. Once the reader has changed a field with a name, the form gets data-dirty, an .unsaved-note in it shows, and leaving the page asks first (that question is the browser’s own). Putting the field back as it was makes the form clean again; so do .saved(), a reset, and a submit that goes on.     Notifications

    Unsaved changes
    • What counts: fields with a name (what a form sends), the kit’s too (a tag box, a date). A search box without a name doesn’t. What the page puts in a field is where it starts: a form filled after it is watched, or drawn again with new values, isn’t changed by that. Only what the reader changes is.
    • Leaving the page: the browser asks while a form is changed, but not when the form’s own submit takes the reader away, and not for a form in a dialog that has closed. Browsers ask only once the reader has done something on the page, and in their own words.
    • Dialogs: one with a changed form in it asks “Discard your changes?” before ×, Cancel, Escape, a click outside or a phone’s back button close it. Its other buttons don’t ask, nor does the page’s own close(). Dash.modal({ unsaved: true }) also shows “Unsaved changes” in its foot.
    • Without code: <form data-unsaved> is watched from the reader’s first press or focus in it. With Dash.form(form, { unsaved: true }), a successful onSubmit is saved.
    • A page that changes what it shows by itself (another view, another record): if (await Dash.unsaved.leave()) show(next). It is true at once when nothing is changed, and otherwise asks; leave(element) asks only about the forms in it.
    • Words: Dash.unsaved.text has the question and its buttons, to translate them. A form drawn again as a whole is followed by its id.

    It returns { el, dirty, changed, saved(), destroy() }: changed is the names of the changed fields; onChange(dirty, handle), an option, is told when it flips. Dash.unsaved on a form that is already watched gives the same handle.
